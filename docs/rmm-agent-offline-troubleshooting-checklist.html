Vendor-neutral RMM agent recovery

Diagnose “offline” before reinstalling.

An offline RMM agent is a failed relationship between endpoint and platform—not automatically a missing service. Use these 24 checks to prove the device state, preserve evidence, isolate the failing layer, protect tenant identity, repair the verified dependency, and confirm every privileged function before closure.

1. Confirm impact

  1. Confirm the endpoint is expected to be online and still in managed scope; rule out planned shutdown, sleep, retirement, or stale inventory.
  2. Record the platform device ID, last heartbeat, last inventory, last successful job, console URL, and displayed time zone before changing anything.
  3. Group affected devices by customer, site, operating system, agent version, policy, network, and first-failure time to distinguish one endpoint from a shared outage.
  4. Confirm approved alternate access, workload criticality, backup state, authority, maintenance window, stop conditions, and customer communication.

2. Verify endpoint state

  1. Use an independent source to confirm power, boot, sleep, network, and isolation state; restore the underlying endpoint first when it is not actually reachable.
  2. Verify the supported agent package, service, startup type, binary path, version, and signature are present and expected.
  3. Capture service state, exit code, process state, crash evidence, and recent start attempts before performing one authorized restart.
  4. Collect agent and operating-system logs for the failure window, preserving timestamps, time zone, first error, and remediation history.

3. Test connectivity

  1. Verify DNS, routing, proxy path, and vendor service status for the exact documented platform endpoints.
  2. Test required outbound ports, TLS negotiation, certificate chain, inspection behavior, and endpoint clock without disabling controls globally.
  3. Review proxy, content-filter, EDR, antivirus, and application-control logs for a specific block or quarantine event.
  4. Confirm trusted time, certificate validity, and trust-store health; repair only the verified narrow dependency.

4. Protect identity

  1. Match local enrollment identity to the intended customer tenant, site, and platform device record before allowing automation to resume.
  2. Search for duplicate, renamed, retired, reimaged, or replacement records using stable hardware and agent identifiers—not hostname alone.
  3. Check whether enrollment credentials, tokens, or certificates were rotated, expired, or revoked and correlate the change to an authorized record.
  4. Separate a heartbeat failure from stale inventory, patching, scripting, or remote-support modules so one broken function does not trigger a destructive reinstall.

5. Repair safely

  1. Define the expected recovery interval, functions to test, success evidence, stop condition, escalation point, and rollback before execution.
  2. Fix the diagnosed service, network, certificate, policy, platform, or resource dependency first and preserve the actor, command or change, time, output, and result.
  3. Prefer the vendor-supported repair path to an immediate reinstall so enrollment identity, configuration, and failure evidence remain intact.
  4. If reinstall is necessary, authorize it explicitly; prove the old agent is removed; control tenant and site placement; and reconcile old and new records before scaling.

6. Validate and close

  1. Confirm a new heartbeat, current inventory, expected agent version, and healthy service state after the documented ingestion interval.
  2. Test monitoring, one bounded script, a fresh patch scan, and remote support separately; capture the corresponding audit evidence.
  3. Reconcile the whole affected cohort into recovered, retired, duplicate, wrong-tenant, offline, unknown, or owned-exception states.
  4. Record the cause, prevention change, monitoring improvement, residual risk, approver, review date, customer acceptance, and closure evidence.

When is an offline RMM agent resolved?

Resolution requires more than a green heartbeat. The endpoint must report under the correct customer and durable device identity; monitoring, scripting, patching, and remote support must produce current results and audit evidence; duplicate or retired records must be reconciled; and every unresolved endpoint must have an owner, due date, escalation path, and time-bounded exception.

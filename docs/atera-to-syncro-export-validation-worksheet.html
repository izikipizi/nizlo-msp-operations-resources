Export Atera to Syncro without mistaking an import for a migration.

Use this source-dated worksheet to preserve Atera records, map ticket states, run Syncro's documented importer, deploy destination agents in a controlled pilot, rebuild what does not transfer, and reconcile every endpoint before source retirement.

How to export Atera data and import it into Syncro

  1. Keep the source exports. Save the ticket, customer and device records you need, along with their filters and row counts. Preserve invoices and required attachments separately. Syncro's importer excludes Atera invoices.
  2. Map ticket statuses first. In Syncro, open Admin → RMM Settings → Migration Tools → Atera. Review the one-time importer instructions and confirm the approved scope with the migration owner before running the import.
  3. Check the queue as a technician. For example, pick one source ticket that was Closed and one that was Pending. Compare the imported IDs and statuses, then check whether each ticket appears in the intended working queue. Syncro says imported Atera tickets do not arrive under its Resolved status. Hold the queue handoff until the owner accounts for any unexpected open work. See the ticket reconciliation example.

Reconcile devices separately after destination agents check in. The device inventory export gives you the source list to match against the destination.

Export the Atera device inventory to Excel

In Atera, open Devices and select or create a table view for the customer or site in your pilot. Include the device name, customer or site, and an available stable device identifier. Use the download icon in the top-right corner to export the view to Excel. Keep the original file with the view filters, export date and row count so another technician can reproduce the scope. 1. Preserve Atera first

There is no single all-data export. Inventory each required entity, keep original files unchanged, record filters and counts, and preserve attachments, invoices, and history that the destination importer does not cover.

2. Map before importing

Create the required Syncro ticket statuses, map customers deliberately, record the approved API rate limit, and test representative records before repeating any uncertain import.

3. Deploy agents as a separate change

Customer and ticket import does not enroll endpoints. Pilot Syncro's documented deployment workflow on authorized, representative devices and prove identity, policy, monitoring, remote access, and rollback.

4. Rebuild and reconcile

Rebuild scripts, monitoring, patching, permissions, and integrations as destination configurations. Run both platforms only within a bounded authority model, then reconcile every endpoint and exception.

Verify ticket summaries after migration

Choose a sanitized pilot ticket with several technician handoffs, a failed troubleshooting step, and an open next action. Reconcile the imported comments and status with the original ticket before evaluating any generated summary.

Have the receiving technician compare the summary to the imported record. Check that it identifies the unresolved issue, retains the failed step, and gives the next technician the correct action. Record the required plan and who can enable the feature. A summary that omits a failed step or makes an unsupported claim should be corrected before the team relies on it.

Worked example with fictional ticket notes

  • 09:10, first technician: Two users report jobs stuck in the shared print queue. A restart of the print service did not clear the queue.
  • 09:35, second technician: A locally generated test page prints, but a new print job from an affected workstation still stalls. The ticket is open, assigned to desktop support, and has a follow-up to reproduce the problem from that workstation.
  • Expected summary: Keep the failure and the pending follow-up. A local test page is evidence of partial function. The affected user's print job remains unverified, so the summary should leave the issue open.

Run the same fixture in each pilot and record the approved plan, who enabled summaries, and how much editing the technician needed. Check disposition and assignee against the imported record. If one tool marks the ticket resolved or skips the failed restart, record that as a failed handoff before comparing time saved.

Verify the destination agent is in the right organization

Suppose all eight pilot devices check in, but two laptops with the same hostname belong to different customers. Match the records using a stable identifier such as the serial number where available, and confirm each device’s intended organization and policy before enabling destination automation.

If a device lands in the wrong organization, record a placement failure even though it is online. Pause that deployment group, correct the source-to-destination mapping, and verify a fresh check-in under the correct organization. Use the first-endpoint acceptance checklist to record the identity, placement, and policy evidence before proceeding.

If a placement failure delays the cutover, record the next date you can verify placement and the last date you can give notice before the next Atera invoice. Open the Atera-to-Syncro first-year cost estimate and increase overlap by the extra billed period. Use the worked quote to document the assumptions. Wait for placement, ticket, and monitoring checks to pass before retiring the old agent.

Preserve or rebuild what does not move

A successful importer receipt is not proof that the destination can deliver the service. Use separate owners and acceptance tests for each gap.

Invoices and attachments

Syncro says Atera invoices are not imported. Atera says bulk exports do not include attachments. Preserve required copies with parent-record mapping, hashes, access control, and retention ownership.

Profiles and automation

Atera says automation settings, thresholds, and monitoring profiles are not exportable. Inventory purpose, assignments, privileges, dependencies, schedules, exceptions, and recovery before rebuilding.

Patch and alert behavior

Validate approval rules, rings, reboots, exclusions, reporting, alert routing, ticket creation, assignment, notifications, escalation, and closure across a representative cycle.

History and acceptance

Preserve required operational history, reconcile source and destination counts, explain every exception, stage credential revocation, and record named operational and business acceptance.

RMM trial activation · First 24 hours · No signup

Do not let an RMM trial end at account creation.

A trial is activated only when an authorized operator can prove one stable endpoint, current telemetry, a safe operational result, an owned exception path, and the next scheduled test. Use this plan to reach that evidence within the first day without widening access prematurely.

Prepared by Kip Ecklund, founder of Nizlo. Vendor relationship disclosed below.

1. Define the first-day outcome before installation

  • Name one accountable trial owner and one backup operator.
  • Select one representative, authorized endpoint—not a production-wide deployment group.
  • Record the endpoint owner, business use, operating system, architecture, network location, and security controls.
  • Set a completion deadline and a shared evidence location.
  • Write the first-day pass condition: one stable identity, fresh telemetry, one safe operational result, a known rollback path, and an owned next action.

2. Confirm fit and rollback authority

  • Verify the vendor currently supports the endpoint's operating system and architecture.
  • Confirm the person installing the agent has authority to do so and knows who may approve exceptions.
  • Identify endpoint protection, application control, proxy, DNS filtering, TLS inspection, and firewall controls before changing anything.
  • Retain the vendor's documented uninstall or removal path and decide what evidence will prove cleanup.
  • Do not disable endpoint protection, expand firewall access broadly, or reuse a tenant credential from another customer to make the test pass.

3. Install once and preserve the evidence

Use the current workspace-specific installer. Record the download source, package version, file signature or checksum when published, execution identity, local and UTC timestamp, exit code, expected service name, and first log location. A completed installer window is not proof that the endpoint enrolled or reported.

If the installer is blocked: record which protection stopped it and the exact warning. Keep protections in place and use the Chrome, SmartScreen, and Defender reporting steps before retrying.

4. Prove endpoint identity and fresh telemetry

  • Confirm exactly one endpoint record appears in the intended workspace, customer, and site.
  • Verify hostname, operating-system build, architecture, and a harmless inventory field against the local device.
  • Confirm the last-seen or check-in time advances after the local service starts.
  • Record the actual first-check-in interval and any delayed inventory fields.
  • If identity or telemetry is missing, stop and use the activation troubleshooting checklist before reinstalling.

5. Run one harmless operational test

Choose a test that fits the authorized scope. Acknowledge a test alert, request read-only inventory, run a preapproved read-only command, or open and close an attended remote-support session. Record the requester, target, timestamp, outcome, and audit evidence.

For a Windows pilot, follow the worked uptime check on one device. A queued job is still pending. Record a pass once the job completes on the intended device and returns the expected boot timestamp. Hold rollout while the job result is missing or points to the wrong device.

6. Exercise the support path while the context is fresh

  • Locate the service state, current log, dashboard status, enrollment identifier, and audit record without relying on the person who installed it.
  • Document where a technician should look first when the endpoint stops checking in.
  • Open a support request only when you can supply sanitized timestamps, versions, failed stage, and reproducible evidence.
  • Record the response channel and expected support clock; do not expose tokens, private keys, user data, or unrelated logs.

8. End the day with a scheduled next test

Choose the next evidence block from what remains uncertain: alert routing, patch reconciliation, automation safety, remote-access authorization, reporting, role separation, API behavior, or clean removal. Give it an owner, endpoint, start time, pass condition, and stop condition. Adding endpoints is not the default next step.

Have a second technician verify the first device

Run this handoff on one approved, noncritical endpoint. The goal is to see whether the next technician can continue from the workspace records alone.

  1. The first technician records the customer and site, device identifier, and last check-in time. They request one approved read-only inventory refresh and record the job reference and result.
  2. Give the second technician the workspace, customer, and ticket reference. Using their usual role, ask them to find the endpoint, the latest inventory result, and the approval record. Record how long it takes and any evidence they have to ask the first technician for.
  3. On the approved test device, take it offline during the pilot window. Ask the second technician to distinguish the last successful inventory from current device status and identify any pending work. Bring the device back online and verify that check-in resumes before closing the ticket.

Pass when the second technician can explain what ran, who authorized it, when the device last reported, and what still needs action. If any answer depends on the first technician’s memory, record the gap and repeat the exercise before expanding the pilot.

Hand off an endpoint that has stopped checking in

Example: The agent service started at 14:05 UTC. The portal showed the correct endpoint at 14:07, but last check-in still read 14:07 at the 14:30 review. The first connection succeeded. Ongoing reporting still needs verification.

Record the expected check-in interval from the vendor, both timestamps, the agent version, and whether the service is still running. Keep that evidence with the pilot owner and use the missing check-in checklist before retrying or widening deployment.

First-day stop rule: do not widen the rollout when the first endpoint lacks a stable identity, fresh telemetry, a controlled test result, a known removal path, or an accountable owner for each exception.

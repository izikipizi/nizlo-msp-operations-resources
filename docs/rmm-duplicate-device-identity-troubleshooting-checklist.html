Vendor-neutral endpoint identity recovery

Reconcile the identity before deleting the duplicate.

Two RMM records do not always mean two agents, and one device that changes identity is not always a harmless naming problem. Use these 24 checks to preserve the evidence, identify whether a golden image, reinstall, shared key, stale import, or integration created the conflict, contain privileged automation, and restore one authoritative identity per endpoint.

1. Confirm the duplicate

  1. Describe the visible conflict: two console objects, one endpoint changing identity, a stale record, or a naming collision.
  2. Capture platform device IDs, local agent or enrollment IDs, tenant, site, hostname, serial number, and hardware UUID from both sides.
  3. Build a timeline for imaging, installation, reinstallation, restore, first and last heartbeat, inventory, jobs, and user activity.
  4. Define the system owner, customer authority, maintenance window, stop conditions, rollback, and communication before cleanup.

2. Preserve identity evidence

  1. Capture the local agent ID, device key or certificate reference, enrollment metadata, install path, and version without modifying them.
  2. Compare serial number, hardware UUID, supported storage identifiers, operating-system install date, and other durable hardware evidence.
  3. Record hostname, domain, IP, MAC addresses, adapters, DHCP history, site, and proxy or NAT context so naming and identity collisions stay separate.
  4. Export record creation, tenant moves, last-seen data, inventory, scripts, patches, alerts, and audit actors before any retirement or merge.

3. Find the root cause

  1. Prove whether the agent was installed or enrolled before a golden image, virtual-machine template, or task sequence was sealed.
  2. Correlate uninstall, reinstall, reimage, or snapshot-restore behavior with the old and new platform records.
  3. Check whether enrollment tokens, keys, certificates, or device identifiers were shared, copied, expired, rotated, or revoked.
  4. Review API requests, imports, connectors, CMDB mappings, retries, and webhooks for duplicate creates or missing idempotency.

4. Contain safely

  1. Pause high-risk scripts, patches, alert actions, and remote access on ambiguous records so one endpoint cannot receive conflicting work.
  2. Quarantine any identity-bearing image, installer, deployment rule, or integration that is still creating duplicates.
  3. Protect tenant boundaries: disable access and automation until customer ownership, tenant, and site placement are proven.
  4. Preserve linked tickets, alerts, patch state, audit history, attachments, and approvals before archiving or retiring anything.

5. Reconcile records

  1. Choose one authoritative endpoint identity using current heartbeat, durable identifiers, ownership, workload, and historical value.
  2. Use only the vendor-supported identity reset, image-preparation, repair, or re-enrollment path; pilot it on one endpoint.
  3. Archive, merge, or retire the non-authoritative object with a reason, approver, retained links, and final evidence; avoid destructive deletion when possible.
  4. Repair downstream CMDB, ticketing, billing, backup, EDR, PSA, documentation, and integration mappings.

6. Validate and prevent

  1. Prove every endpoint has one unique active identity in the correct tenant and site after the documented ingestion interval.
  2. Test current inventory, monitoring, a bounded script, patch scan, and remote support separately and retain their audit evidence.
  3. Sweep the affected image, deployment, agent-version, tenant, and site cohorts for hidden duplicates or cross-tenant exceptions.
  4. Correct image timing, enrollment handling, API idempotency, duplicate detection, runbooks, owners, and review dates.

Primary documentation to pair with this workflow

This checklist organizes evidence and decisions; it does not replace the current procedure for the operating system or installed agent. Microsoft documents that a Windows image must be generalized before deployment to another computer. Datto RMM documents how locally stored agent identity and reused network adapters can create cloned or duplicate records. Liongard documents detection and supported reset behavior for duplicate agent identities. Before changing an identifier, key, certificate, file, registry value, enrollment, or platform record, use the exact current procedure for the affected product and retain the evidence required by your customer and security controls.

  • Microsoft Learn: Sysprep (Generalize) a Windows installation
  • Datto RMM: cloning or imaging devices with the agent installed
  • Liongard: duplicate agents

When is a duplicate RMM device resolved?

Resolution requires one unique active identity for each managed endpoint, correct customer and site placement, current functional results, preserved operational history, repaired downstream mappings, and an owned disposition for every stale or conflicting object. A renamed duplicate, hidden record, or deleted object without retained evidence is not reconciliation.

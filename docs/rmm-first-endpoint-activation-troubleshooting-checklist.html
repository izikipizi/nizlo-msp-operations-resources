Get your first RMM endpoint to check in

Do not treat “downloaded,” “ran,” “installed,” “enrolled,” and “reporting” as the same event. Find the first missing proof, correct only that stage, and preserve enough evidence to reproduce the result.

Where did setup stop?

  • Nizlo is still preparing the Windows installer
  • Chrome or Windows showed a warning
  • The download started or the file is ready
  • The installer ran and the device has never checked in
Did this endpoint report successfully before? If it has never reported, start with the activation checklist below. If it previously reported and is now missing or stale, preserve its device ID, last known heartbeat, and active console filters, then use The First 15 Minutes After an RMM Endpoint Disappears, published by Techwrix and written by Nizlo founder Kip Ecklund.

Prepared an installer? Resume on the device you want to manage

Preparing or downloading the installer leaves the device list unchanged until the agent runs on the target computer and checks in.

If a download started, open the target computer's browser downloads list and confirm the file finished saving before you try to run it. If it is incomplete and the installer setup is still open, choose Download MSI again for Windows or Download again for Mac or Linux. This retries the prepared package. If the setup is closed or the link has expired, return to Enrollment in the same workspace and prepare one fresh package. If a browser or Windows warning stopped it, record the warning and verify the installer source before retrying.

  1. Open Nizlo Enrollment in your existing workspace. Select Install agent and verify the customer, site, and platform for the authorized test computer.
  2. If you prepared the package from your own workstation, use your approved software delivery method to get the workspace-specific installer onto the target computer. Keep private installer links and enrollment credentials within that approved workflow. If the original download link has expired or was scoped to the wrong customer or site, prepare a fresh, correctly scoped package.
  3. Run the installer on the target computer with the required permissions. In the same Nizlo workspace, confirm the expected hostname, customer, site, and a fresh check-in. If the device is still absent, preserve the exact result and use the local service and enrollment checks below before reinstalling.

1. Define exactly what failed

Record the last stage you can prove, the first stage you cannot prove, the endpoint name, operating system build, architecture, installer version, local time and UTC time. A dashboard with no endpoint does not prove that the installer never ran; an installed service does not prove enrollment.

2. Verify the test is authorized and supported

  • Use a designated test endpoint with an owner and rollback plan.
  • Confirm the operating system, edition, architecture, and required runtime match the vendor's current support documentation.
  • Verify the installer is current and came from the intended workspace or customer.
  • Check file integrity or signature when the vendor publishes a signature or checksum.
  • Run with the documented elevation level. Capture the exit code rather than assuming a quiet installer succeeded.

When Nizlo is still preparing the Windows installer

Waiting for signing or Signing your installer means the workspace-specific package is still being prepared. Leave the setup open while that message is displayed. Check the browser’s downloads list after the file is offered.

If the wait ends with a message that signing is taking longer than usual, select Download MSI in the same setup to reuse that preparation. If the arrow beside it offers Download ZIP · clean filenames, use the signed setup provided by your workspace and follow the included instructions. Keep the ZIP and its contents within your approved deployment process.

If preparation still stalls, contact Nizlo Support with the displayed status and the approximate time. Keep private setup files, links, and enrollment tokens out of the message. If the browser or Windows actually blocked a file, follow the warning evidence steps with protections enabled.

When Chrome or Windows blocks the installer

Pause the installation and keep the protection enabled. Record where the warning appeared and where you obtained the file. If someone sent you an installer link or attachment outside your approved deployment process, leave it unopened and report the source to your IT team.

  • Chrome blocks the download. Open Chrome's Downloads list and capture the exact warning and filename if shown. Include your Chrome version. Chrome download warnings
  • Windows displays SmartScreen after you open the file. Record the exact warning, publisher if shown, and your Windows version. Windows app and browser control
  • Microsoft Defender flags or quarantines the file. If authorized, look in Windows Security > Protection history for the detection name, action, and time. Leave quarantined files in place. Windows Protection history

Send the warning text, the approximate time and time zone, and the source of the installer to your vendor. Include the filename only after removing any workspace-specific enrollment details. Keep private download links and enrollment tokens out of messages and screenshots.

If you prepared the file from Nizlo's Enrollment page, share those details with Nizlo Support before retrying. A filename or displayed publisher helps identify the package. Support can use it with the preparation time to check the specific file.

3. Verify local agent state

  • Locate the documented service, process, installation directory, and log path.
  • Record whether the service is missing, stopped, repeatedly restarting, or stable.
  • Review the newest relevant log lines around the attempted installation and first start.
  • Check endpoint-security, application-control, quarantine, and operating-system event logs for a matching block.

Do not disable endpoint protection as a diagnostic shortcut. If evidence shows a block, use a narrow, time-bounded exception approved through your normal change process, then remove it after the test.

4. Verify identity and enrollment data

  • Confirm the workspace, tenant, customer, site, token, or enrollment code belongs to the intended destination.
  • Check whether the enrollment credential expired, was revoked, or was copied with extra characters.
  • Search for a stale or duplicate endpoint identity before creating another record. If this is a Nizlo device, check whether the endpoint was archived.
  • Do not delete an existing record until you know what audit history, policy assignment, or billing data deletion would remove.
Two records for one machine? Before retrying enrollment, use the duplicate device checklist to compare device IDs, serial number, customer and site, and last check-in. If you find a single archived Nizlo record, use the restore steps below.

Restore an archived Nizlo endpoint before reinstalling

Archiving removes the device from active views and blocks its agent from connecting. It keeps the existing device record and leaves the software installed on the computer.

  1. In Endpoints, select Archived endpoints. Confirm the device, customer, and site before selecting Restore endpoint on an authorized device. An installed agent may resume check-in on its existing record. Cancelled jobs and resolved alerts stay closed.
  2. Confirm that one device record shows a fresh check-in in the expected customer and site. If the installer instead says Device identity is already enrolled, keep the existing record and note the exact error. Re-running the installer with the same identity can hit the same conflict.
  3. For a brand-new pilot record, use a separate authorized test device or ask Nizlo Support for the supported recovery steps. Include the device ID, operating system, and approximate time. Leave enrollment tokens and private installer links out of the message.

5. Verify DNS, time, TLS, proxy, and egress

  • Resolve only the vendor-documented hostnames from the endpoint's actual network.
  • Confirm system time and time zone are accurate enough for certificate and token validation.
  • Test the documented outbound ports—commonly HTTPS on TCP 443—without inventing broad firewall rules.
  • Check whether a proxy requires authentication or whether TLS inspection substitutes a certificate the agent rejects.
  • Capture the hostname, timestamp, result, and applicable proxy or firewall log. Do not paste enrollment tokens or private keys into a ticket.

Windows read-only evidence commands

Use the vendor's documented service name and control-plane hostname. These examples collect state; they do not change a service, proxy, firewall, certificate store, or clock. Run only on an authorized endpoint and retain the command, timestamp, output, and execution identity.

  • sc.exe query <agent-service-name> — prove whether the expected Windows service exists and record its current state, exit code, checkpoint, and wait hint.
  • Resolve-DnsName <documented-control-plane-host> — capture the endpoint's actual DNS answer instead of assuming the browser and service resolve the same path.
  • Test-NetConnection <documented-control-plane-host> -Port 443 -InformationLevel Detailed — record name resolution, source interface, remote address, route context, and whether the documented TCP connection succeeds.
  • netsh winhttp show proxy — inspect the machine WinHTTP proxy used by many services; do not reset or import proxy settings merely because they differ from the interactive browser.
  • w32tm /query /status — record the Windows Time service source, stratum, last synchronization, and offset-related state before investigating token or certificate timing failures.

A successful TCP test does not prove TLS, application authentication, enrollment, or telemetry. A failed test does not identify the cause by itself. Correlate the result with vendor-documented destinations, proxy or firewall logs, agent logs, and the exact UTC timestamp.

6. Restart or reinstall only after the evidence points there

Restart the documented service once and observe whether the failure changes. Reinstall only when the installed files, service registration, or package state is demonstrably incomplete. Repeated reinstall attempts can erase the first useful log, create duplicate identities, and hide the original cause.

7. Prove activation in the dashboard

  • Verify the endpoint appears in the intended tenant and site with one stable identity.
  • Confirm the dashboard timestamp advances after the local service starts.
  • Compare a harmless property—such as OS build or hostname—between the endpoint and dashboard.
  • Wait for the documented initial check-in interval; record the actual interval instead of relying on a page refresh.
  • Continue to the first-endpoint acceptance checklist only after fresh telemetry is proven.

The first endpoint is online, but inventory is empty

In this example, the workstation's last check-in advances from 10:04 to 10:09 UTC, but its operating system and software inventory still show no data. Check that both views reference the same device ID in the intended customer and site. Record the two timestamps and which inventory fields are missing.

Record check-in as passed and inventory verification as pending. Allow the vendor's documented initial collection interval, or ask support for the expected interval if it is unclear. If the data still has not appeared, send the current device ID, timestamps and missing fields to support before retrying the installation. Verify one harmless value, such as the OS build, against the workstation before accepting the pilot.

Use the first-endpoint acceptance checklist to record the retest. If several pilot devices are affected, reconcile each device against the approved inventory before expanding.

An unexpected device checked in briefly

Datto documents that automated security analysis can run a site-specific agent installer and create a short-lived device record. A cloud IP, a Hyper-V MAC address, or a brief check-in is a clue. Confirm the device against an approved inventory record before classifying it or acting on it. Datto mystery device records.

Record the first and last check-in in UTC, the RMM device ID and site, and the deployment batch. If the installer was assigned through Intune, compare the expected device and assignment with the app’s Device install status. An absent match is a reason to investigate further. Share the evidence through the vendor’s private support channel and keep the unexplained record out of the pilot acceptance count. Microsoft Intune app monitoring.

Check the Intune client logs on the approved workstation

Compare the RMM check-in time with AppWorkload.log for Win32 app installation and AppActionProcessor.log for detection and applicability. Match the serial number or another stable device identifier where available. Share the timeline and device IDs with the vendor before attributing the record to a specific security product. Preserve the audit history and leave endpoint protection enabled while investigating. Microsoft's Win32 app troubleshooting guide.

Worked example with two approved devices

Suppose two laptops are approved for an Intune pilot. The first has a matching inventory record and checks in at the intended RMM site. The second shows a successful Intune install, but its RMM record appears in a different site. A third device ID appears briefly and has no matching assignment. Record one correctly placed check-in out of two approved devices. Keep the second pending while you correct its placement and verify it again. Log the third separately for investigation. Run the acceptance checks before counting either approved laptop as ready for rollout.

Give the Intune deployment owner the assignment and installation evidence. Give the RMM owner the customer, site, and heartbeat evidence. Require both owners to sign off when Intune deploys the agent. Nizlo's Intune vs. RMM guide shows where to assign policy, patching, monitoring, and support when you keep both tools.

Keep scripts and remote actions off the unexplained record while you investigate. For Datto, evaluate New Device Approval in a controlled rollout with an assigned approver and a test of the normal Intune deployment. Datto documents that devices awaiting approval can send audit data while jobs, policies and remote takeover remain blocked. Datto device approval.

Follow the Intune and RMM field notes for more deployment checks.

8. Send a first-endpoint support ticket

Copy this outline into your vendor’s support form. Fill the fields you can verify and leave the rest as unknown. If the endpoint has never checked in, say so and use the last confirmed setup step instead of guessing at the cause.

  • Subject — First test endpoint missing after [last confirmed step]
  • Workspace and device — Workspace identifier and endpoint ID if one exists. Share these in your vendor’s private support channel.
  • Attempt — UTC time, target OS and architecture, installer or agent version, and whether preparing, downloading, running, or checking in was the last confirmed step.
  • Expected and observed — Expected device and site, exact error or exit code, and one sanitized log line or screenshot if available.
  • Tests already run — What you checked, any reversible changes you made, and the result. Attach DNS, TLS, proxy or security-control evidence only if it bears on the failed stage.

Redact private installer URLs, tokens, credentials, customer data and unrelated log lines before sending. For Nizlo trials, use Nizlo Support.

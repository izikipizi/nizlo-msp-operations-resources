Use this MSP client offboarding checklist to coordinate service handoff, access revocation, RMM agent removal, data disposition, residual exceptions, customer acceptance, and post-exit verification.

Authorize the exit

Record the approved end date, decision owners, scope, constraints, successor, service cutoff, and communication path before changing access or agents. If the service transition includes replacing the RMM, coordinate the commercial and technical controls in the vendor exit plan.

Transfer with evidence

Reconcile endpoints, accounts, vendors, licenses, documentation, backups, incidents, and open work. Start from a source-dated endpoint inventory, then name the authorized recipient and acceptance owner for each handoff.

Revoke every access path

Disable interactive, service, API, emergency, delegated, VPN, vault, cloud, and vendor-portal access. Revoke tokens and sessions, then verify removal from both sides.

Verify after cutoff

Track failed agent removals and retained data as exceptions, obtain customer acceptance, and monitor for unexpected authentication, check-ins, jobs, alerts, or data flows.

Safe use: do not place passwords, secrets, recovery codes, private keys, tokens, backup contents, or regulated customer data in this register. Store sensitive transfers in an approved encrypted channel and record only the evidence reference.

MSP client offboarding FAQ

What belongs in the checklist?

Cover authority and dates, inventories, service and documentation handoff, every access path, RMM and remote-support removal, vendor transfers, data disposition, acceptance, exceptions, and post-exit monitoring.

How is access revocation proved?

Inventory interactive, service, API, delegated, VPN, vault, cloud, and vendor-portal access; revoke credentials, tokens, sessions, and trust; then capture independent evidence that access no longer works.

How should RMM agents be removed?

Freeze the starting inventory, remove in controlled waves, verify services and processes are gone, reconcile multiple inventory sources, and track failures through closure. Use the agent uninstall verification checklist for the detailed proof steps.

When is offboarding complete?

Only after handoff, access removal, agent removal, data disposition, exceptions, customer acceptance, and post-cutoff monitoring are all evidenced—not merely when a contract ends.

Control basis: CISA’s MSP guidance tells customers to disable MSP accounts after the provider no longer manages infrastructure and recommends least privilege, account and infrastructure hygiene, logging, backup protection, and clear responsibility. NIST CSF 2.0 supports managed identities, revoked credentials, asset lifecycle control, and documented risk treatment. Field perspectives: Current MSP transition playbooks from Slyder Consulting Group, Robb Technology Group, Datapath, CTO Input, and Stedra's guide to a clean outgoing-MSP handoff independently emphasize staged transitions, explicit ownership, usable documentation exports, verified backup access, temporary overlap, documented access transfer, controlled agent removal, and post-cutover verification. This register turns those recurring operational themes into assignable controls and evidence fields. Stedra did not create, review, or endorse this register.
Transition safeguards: Nibelka Ventura's current Stratify IT guide to switching MSPs adds practical safeguards: audit the full environment before cutover, run parallel monitoring until the destination is stable, define rollback criteria before migration, assign an internal decision owner, and record insurance and contract constraints. The register maps those themes to scope, schedule, coverage-validation, owner, constraint, evidence, and exception fields. Stratify IT did not create, review, or endorse this register.

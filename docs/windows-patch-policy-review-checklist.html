RMM patch management policy checklist for Windows

An RMM patch management policy should define which Windows devices and update classes are in scope, how deployment rings promote, when deadlines and restarts apply, who approves exceptions, how failures roll back, and what evidence closes each cycle. Use these 24 checks to review that policy before the next deployment.

1. Authority and scope

  1. Name the policy owner, approving authority, effective date, version, and next review date.
  2. Define included tenants, device classes, operating-system editions, locations, and supported ownership models.
  3. List exclusions explicitly and assign each exclusion an owner and compensating control.

2. Update classification

  1. Separate security, quality, driver, firmware, feature, and emergency updates.
  2. State which update sources and approval channels are authoritative.
  3. Define when an emergency change can bypass the standard cadence and who records the decision.

3. Rings and promotion

  1. Define representative lab, pilot, early-production, and broad-production rings.
  2. Set minimum observation time and measurable promotion criteria for every ring.
  3. Specify stop conditions for crashes, service degradation, application failure, or unexpected restart behavior.

4. Deadlines and restarts

  1. Set deployment and completion deadlines by update severity.
  2. Document maintenance windows, user notices, restart deferrals, and forced-restart limits.
  3. Define treatment for offline, sleeping, bandwidth-constrained, and rarely connected devices.

5. Exceptions

  1. Require a business reason, affected scope, risk statement, approver, and expiry date.
  2. Assign monitoring and compensating controls while the exception remains open.
  3. Require retest, disposition, and closure evidence so deferrals cannot become permanent by default.

6. Failure and rollback

  1. Define rollback triggers and the person authorized to stop or reverse a deployment.
  2. Document recovery prerequisites, backups, known-uninstall paths, and service-specific restoration steps.
  3. State how failed devices are isolated, triaged, reconciled, and returned to a supported state.

7. Evidence and reporting

  1. Record approval, targeting, timestamps, install results, restart state, and device-level exceptions.
  2. Reconcile discovered, targeted, installed, failed, excluded, offline, and unknown device counts.
  3. Define the cycle-close report, its audience, retention period, and link to unresolved work.

8. Testing and review

  1. Test policy behavior on representative devices before broad rollout.
  2. Review missed deadlines, false success, noisy exceptions, rollback use, and recurring failure patterns.
  3. Reapprove the policy after material tooling, client, regulatory, or operating-model changes.

Test what happens after a Windows device misses its patch window

On an authorized pilot laptop, record the intended install and restart behavior before testing. Keep it offline through the scheduled window, then reconnect it outside that window. Record when it checks in, whether it queues or installs the update, and whether it restarts, prompts, or waits. Check the endpoint state after the next allowed window and compare it with the dashboard and exported report.

For example, suppose a pilot targets eight devices. Five have verified installation, one is awaiting restart, one is deferred, and one is still offline. Record five of eight as verified complete and keep the other three outcomes visible. Assign an owner and a next check time for each open outcome. If it is unclear whether the missed device can install or restart during business hours, repeat the test before expanding the rollout.

Use the patch failure triage checklist when an endpoint comes back online but the installation still cannot be verified. The worked fleet coverage example shows how to reconcile counts before approving the next ring.

Test Windows update ownership when Autopatch and RMM overlap

Start with one authorized pilot device. Record its assigned quality update policy, update ring, approval state, deferral, deadline, and grace period. Microsoft documents that the Autopatch quality update policy takes priority for approvals and deferrals when both policies apply, while the ring still supplies settings such as deadlines and grace periods. Check Microsoft's precedence rules for Windows quality updates.

For that cohort, record which tool authorizes the install and restart and which tool observes the result. If Autopatch owns Windows quality updates, verify that the RMM is only reporting on those updates for the pilot. Keep any separately approved third-party app workflow under its own owner and scope. Before expanding, compare the expected schedule with the actual install, restart, and fresh scan evidence on the device.

Check whether Hotpatch still needs a restart

Record the pilot device’s update type and baseline before judging a restart. A Hotpatch security update on a current baseline takes effect without a restart, but the baseline update itself requires one. A device that falls behind the baseline can still need a restart in a Hotpatch month. Confirm the update type in Microsoft’s Hotpatch guidance and record the installed update, restart state, and next planned window before changing either tool’s policy.

Definition of review-ready

A patch policy is review-ready when another authorized operator can identify its scope, make the same promotion and exception decisions, stop an unsafe deployment, locate the required evidence, and prove that every endpoint has a known disposition. A green dashboard alone is not closure if failed, offline, excluded, or unknown devices are not reconciled.

Prove an update for one third-party app

Pick a representative app your team is responsible for updating. On one authorized test endpoint, record the installed version, the approved target version, and the source for the update. Confirm which tool can identify an outdated version and which tool can actually install the approved update.

After the test install, check that the running app reports the target version and that the user's essential workflow still works. Record any restart, failure, or stalled update separately. If the pilot only proves inventory, keep the app assigned to your existing patch tool with a named owner. See Nizlo's Windows Update scope and pilot checks for an example of how a vendor documents that boundary.

Count a third-party update only after checking the running version

A catalog match tells you that a package is listed. For the app you need, record the supported update channel and architecture, then collect separate evidence of detection, installation and the running version on an authorized pilot device.

For example, target the same app update on 12 pilot devices. Eight run the approved version and pass the smoke test. Two have an install receipt and still need an app restart before you can check the running version. One installation failed and one device is offline. Report 8 of 12 verified updates and keep the four open outcomes separate. Assign an owner and a next check to each, then use the fleet coverage example when reporting the broader rollout.
